## 2. Outcome

A clean repository checkout builds and installs a minimal development package and runs the same documented source checks in CI. The only exposed CLI behavior is implemented, truthful version/help behavior.

## Required input package

- Merged BOOT package and accepted architecture/source hash.
- Observed new-repository layout and instructions; BOOT-000 root receipt and RB11 startup/automation records. BOOT must be integrated with required checks passed.
- Exact proposed source-CI triggers, permissions and runner ownership; current controls and any actual existing check contexts. Verify current settings rather than importing values from an earlier repository.
- Chosen supported development Python/build/test tooling with exact reviewed versions and dependency/license records.

## Allowed source areas — convert to an exact allowlist at activation

- A narrowly scoped new-source CI workflow under `.github/workflows/`; exact paths and effects belong in the activated allowlist. Root license/notices and adopted instruction templates are explicitly included in that list. Broader repository settings remain separately bounded.

## Implementation requirements

- Source checks address only the new implementation and its owned fixtures. Exclude historical reference documents and executable experiments from runtime/build artifacts. Do not add legacy check names, required imports or old source lookups.

## Meaningful proposed acceptance tests

- Build then install from a clean checkout/environment; run version/help without importing legacy files.
- Check wheel/package inventory excludes Git metadata, credentials and executable experimental seeds.
- Run the same named checks locally and in source CI; deliberate packaging/test fixture failure makes the relevant check fail. Use a separate controlled scanner-policy negative fixture, and verify required scan errors/unavailable execution cannot yield a passing vulnerability check. Do not execute exploit code to demonstrate a finding.
- Inspect actual workflow trigger/permission/runner behavior, action pins and dependency input closure; demonstrate routine source checks cannot provision Hetzner or obtain release/production authority. Record unobservable properties as gaps, not passing assertions.
- Non-TTY version/help output is plain, finite and secret-free; unsupported invocation reports an honest error.

## Documentation and changelog work

- Contributor setup and exact check commands, expected outcomes and supported tooling.
- Source-CI scope and real check names versus later installed release-test qualification. Distinguish a configured required check from a manual acceptance gate.
- Initial changelog entry describing a development skeleton, not a working installer.

## Excluded from this slice

- No deployment, firewall/SSH change, privileged executor, persistent journal or Drupal installation.
- No unscoped repository settings change, inherited source import, existing-site migration or unrelated repository operation.
- No published release/signing claims and no tests labeled full G01 PASS merely from a package smoke test.
