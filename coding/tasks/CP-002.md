## 2. Outcome

Implemented and integrated the first configuration schema, strict parser, canonical byte representation and explicit default-origin model. Inputs that cannot represent an accepted ready configuration fail without writes.

## Required input package

- CP-001 installed package/check setup.
- Accepted initial version 1.0.0, JSON Schema 2020-12 and §18.5 field groups.
- Reviewed maintained JCS implementation and exact parser/validator versions with conformance vectors.

## Allowed source areas — convert to an exact allowlist at activation

- Configuration and common scalar definitions under `schemas/`.
- Parser/default/canonicalization modules under `src/actools/` or `src/actools/contracts/`.
- `tests/` adversarial configuration and JCS conformance fixtures.
- Configuration reference and relevant contract ADR.

## Implementation requirements

- Use one JSON data model for strict YAML and JSON; reject duplicate/unknown fields, custom tags/merges, ambiguous types, nonfinite numbers and invalid Unicode. Preserve omitted/null/false and string distinctions.
- Enforce the accepted 1 MiB and 32-level parser starting limits and finite collection/string bounds. Larger later manifests require their own bounded schemas.
- Enable required format assertions and semantic cross-field checks, not only structural validation. Distinguish endpoints, filesystem authority IDs, domains and secret references.
- Use bounded safe integers; exact larger numbers/decimals need explicit constrained string contracts. Sorted keys alone are not JCS.
- Resolve defaults once with their reviewed policy/release origin and reject unsupported profiles/inline credentials. Configuration acceptance does not assert that unimplemented capabilities are ready.
- Keep unfinished wizard answers out of the ready schema. No persisted draft format or secret generation is introduced.

## Meaningful proposed acceptance tests

- Published JCS vectors and representative Unicode/number distinctions yield expected bytes or a clear rejection.
- Duplicate keys, unknown properties, ambiguous YAML booleans/types, tags/merges, bad Unicode and oversized/deep inputs fail deterministically.
- Equivalent supported YAML/JSON values resolve equivalent configuration/default origins.
- Rejected input containing synthetic secret canaries does not expose values in exception/output text.
- Ready config validation changes no managed paths, journal, baseline or secrets.

## Documentation and changelog work

- Configuration field ownership, units, defaults/origins and supported profile versus readiness distinctions.
- Safe redacted validation errors and how to correct an input.
- Parser/validator/canonicalization dependency and compatibility ADR.

## Excluded from this slice

- No wizard UI, filesystem publication, host inspection, plan/apply or secret-value loading yet.
- Do not weaken strict parsing to accept a legacy shell configuration.
