## 2. Outcome

Create the initial source-owned capability/requirement graph and versioned schema family boundaries needed by the first installed slice. Make support, observations and admission distinct before execution code depends on them.

## Required input package

- CP-002 parser/default/canonicalization implementation and exact versions.
- Architecture F/WP/G registers, §18.3 dispositions and Annex UX/UXS requirements.
- Initial closed action vocabulary and command/result/plan field groups in §18.5.

## Allowed source areas — convert to an exact allowlist at activation

- Graph and policy data under `policies/`; schemas under `schemas/`.
- Contract models/version dispatch under `src/actools/contracts/`.
- Graph-validation, schema-equivalence and versioned fixtures under `tests/`.
- Contract catalog and capability/CLI/evidence vocabulary documentation.

## Implementation requirements

- Separate accepted/deferred decision status, implementation status, advertised support and runtime evidence. Workers/PITR/Phase 2 UI cannot become available because a schema name exists.
- Define owned field groups and reader/writer compatibility for configuration, plan, journal, graph, release, evidence and backup set. Fully validate fields required by the fixture slice; later typed refinements must land before their handlers, never through permissive arbitrary dictionaries.
- Plan data includes exact action/request, targets/effects, significant state/digests, authority requirements, deadlines, disruption/recovery and review identity. It carries no executable command text.
- Define versioned result/envelope semantics including one JSON result, durable operation outcome versus delivery result, safe next-action IDs and source disclosure.
- Model finding status, severity, gate disposition, run state and both coverage denominators separately. Implement deterministic pure evaluation fixtures for initial controls; missing proof cannot become PASS.
- Register accepted HTML diagnostic enumeration and presentation metadata without implementing a renderer/service. Fix who owns captured/evaluated/rendered times and artifact references.
- Unknown future contract versions reject without mutation; generated models/docs must match schemas. Initial graph completeness is checked against the architecture, and unresolved exact test mappings remain explicit work, not false support.

## Meaningful proposed acceptance tests

- Invalid graph dependency/duplicate ID/unowned capability or falsely implemented deferred capability fails validation.
- Significant plan-field changes alter canonical identity; omission/type/version errors reject.
- Known failure plus missing evidence yields incomplete coverage and preserved factual failure, according to §12.1 precedence.
- Caller-edited/rehashed result or presentation cannot create authenticated admission evidence.
- Versioned cross-model fixtures preserve field/default/enum semantics; initial backup set distinguishes commit checks from later restore proof.

## Documentation and changelog work

- Contract owner/version/migration matrix and graph versus task ledger authority.
- Output/status/coverage/exit vocabulary with clearly labeled examples.
- Exact plan review and evidence provenance explanation.

## Excluded from this slice

- No privileged executor, effect handlers, collection schedule or report rendering.
- No new draft schema, action command family, second registry/evaluator or admission authority.

## Coding, review and evidence handoff

Deliver one complete change against the recorded base through the selected route: a patch/complete-file set under RB02/RB10, or a verified direct GitHub candidate under [RB12](../runbooks/RB12_DIRECT_GITHUB_OPERATIONS.md). Include the actual delivery manifest, full changed-file inventory/content, concise design explanation, exact test commands, expected assertions and documentation changes. Direct source delivery uses actual returned commit/tree identities and read-back; it does not invent a local artifact or checkout. State separately which checks were actually run, where, on which candidate and their results. If chat cannot execute them, label them pending and let the human run them. Do not say “all tests pass” from inspection alone.

The reviewer examines exact code plus surrounding interfaces and the test quality, then records findings with severity, consequence, correction and retest need. The human performs applicable devbox tests after review of privileged changes; these initial cards chiefly use isolated local/source-CI fixtures. A release-test installation is added when the installed slice exists, not fabricated for an earlier parser task.

For any shared schema, result contract or security-helper change, identify directly affected existing consumers and include meaningful consumer compatibility/integration checks alongside producer tests. If a consumer does not exist yet, record the gap and assign integration to its first consuming task. After a fix, identify invalidated evidence and rerun the affected checks. Update help/runbook/config/error examples when behavior changes. On acceptance record actual base/candidate/merge, reviewer disposition, evidence and docs references in `records/TASK_LEDGER.csv`. Update the user-facing changelog only with implemented behavior and known limits. No product-wide G gate becomes PASS merely because this slice's unit fixtures pass.
